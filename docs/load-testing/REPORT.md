## Сценарий и объём

Два независимых `constant-arrival-rate` исполнителя: по 50 итераций/с для GET `/api/v1/airports` и GET `/api/v1/flights`. Одна итерация содержит ровно один HTTP-запрос. Перед измерением -- 20 секунд прогрева по 10 запросов/с на endpoint; измерение -- 60 секунд. На endpoint предварительно выделено 50 VU, предел -- 100; для прогрева -- 10 и 20 соответственно. HTTP-таймаут -- 5 секунд, graceful stop -- 10 секунд. Соединения переиспользуются.

Параметр `limit=50`. Каждая пятая итерация VU при наличии курсора читает следующую страницу. В подтверждающем прогоне таких запросов 1200 из 6002 (20%); остальные 4802 читают первую страницу. Проверяется статус 200, структура страницы и согласованность `has_more`/`next_cursor`, наличие строковых ID и известного `X-Backend-Instance`.

### Балансировка

Распределение определено по заголовку `X-Backend-Instance` каждого измеренного ответа:

| Экземпляр | Запросов | Доля | Цель |
|---|---:|---:|---|
| `api` | 3000 | 49,98% | 45–55% |
| `api-read-1` | 1501 | 25,01% | 20–30% |
| `api-read-2` | 1501 | 25,01% | 20–30% |

Полученное распределение соответствует весам 2:1:1. Оба read-only экземпляра участвовали в обработке запросов.

## Выводы

1. Для выбранной смеси публичных чтений и `limit=50` требование p95 < 500 мс при суммарных 100 запросах/с выполнено.
2. HTTP-ошибок, некорректных страниц и пропущенных итераций нет. Распределение чтения соответствует 2:1:1.
3. Flights отвечают медленнее airports, но обе задержки существенно ниже заданного порога.
