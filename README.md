# Airline Tracker

Airline Tracker — система для просмотра рейсов и отслеживания изменений в их расписании. Она объединяет публичный каталог рейсов, личные подписки пассажиров и интерфейс администратора для управления аэропортами, воздушными судами и рейсами. При изменении рейса система формирует уведомления для подписанных пользователей и асинхронно отправляет их по электронной почте.

## Цель работы

Цель проекта — сократить время между изменением оперативной информации о рейсе и получением этой информации пассажиром. Система предоставляет единый источник сведений о рейсах, позволяет пользователю подписаться на интересующий рейс, а администратору — поддерживать расписание и справочники в актуальном состоянии.

## Требования

### Функциональные требования

- любой посетитель может просматривать список рейсов, сведения об аэропортах и подробности выбранного рейса;
- пользователь может зарегистрироваться, войти в систему и выйти из неё;
- авторизованный пользователь может подписаться на рейс и просматривать свои подписки;
- администратор может создавать аэропорты, выходы на посадку, модели самолётов, самолёты и рейсы;
- администратор может изменять расписание, фактическое время, статус и план рейса;
- при создании подписки и изменении рейса система формирует уведомление и доставляет его пользователю по электронной почте;
- система проверяет целостность маршрута: существование самолёта, аэропортов и выходов, различие аэропортов вылета и прилёта и корректный порядок времени вылета и прилёта.

### Ключевые нефункциональные требования

Указанные значения являются критериями приёмки и требуют отдельного нагрузочного и эксплуатационного тестирования.

| Категория | Измеримое требование |
|---|---|
| Производительность | Для `GET /api/v1/flights` и `GET /api/v1/airports` 95-й перцентиль времени ответа не должен превышать 500 мс при нагрузке 100 запросов в секунду после прогрева кэша. |
| Надёжность | Не менее 99,5% доступности за календарный месяц; неотправленные события должны сохраняться в таблице `outbox` и повторно обрабатываться после восстановления Kafka с интервалом опроса не более 1 секунды. |
| Безопасность | 100% операций пользователя и администратора должны отклонять запрос без действительного JWT и требуемой роли; срок действия JWT — не более 15 минут, пароли хранятся только как bcrypt-хэши. |

## Пользовательские сценарии

### 1. Просмотр рейсов

**Актор:** посетитель.

**Предусловие:** приложение доступно.

**Основной поток:** посетитель открывает приложение → система загружает аэропорты и рейсы → посетитель использует поиск и выбирает рейс → система показывает маршрут, расписание и текущий статус.

**Результат:** посетитель получает актуальную информацию без обязательной авторизации.

### 2. Подписка на рейс

**Актор:** зарегистрированный пользователь.

**Предусловие:** пользователь авторизован, рейс существует.

**Основной поток:** пользователь выбирает рейс → нажимает кнопку подписки → API проверяет пользователя и рейс → создаёт уникальную подписку → сохраняет событие в `outbox` → уведомление передаётся через Kafka в сервис уведомлений.

**Альтернативы:** при недействительном токене возвращается `401`; при отсутствии пользователя или рейса — `404`; повторная подписка не создаёт дубликат.

**Результат:** рейс появляется в списке подписок пользователя.

### 3. Создание рейса

**Актор:** администратор.

**Предусловие:** администратор авторизован; самолёт, аэропорты и соответствующие выходы существуют.

**Основной поток:** администратор заполняет форму → система проверяет роль и входные данные → проверяет маршрут и время → сохраняет рейс и его маршрут → возвращает подтверждение создания.

**Альтернативы:** система отклоняет запрос, если аэропорты совпадают, сущности не существуют, выход не относится к выбранному аэропорту или прилёт запланирован раньше вылета.

**Результат:** новый рейс доступен в общем списке.

### 4. Изменение рейса и уведомление пассажиров

**Актор:** администратор; получатели — подписанные пользователи.

**Предусловие:** рейс существует, на него есть подписки.

**Основной поток:** администратор меняет расписание или статус → API обновляет данные и создаёт событие → издатель передаёт событие в Kafka → notifier сохраняет уведомления → отправитель доставляет письма и отмечает уведомления отправленными.

**Альтернатива:** если брокер временно недоступен, событие остаётся в `outbox` для следующей попытки.

**Результат:** подписчики получают сведения об изменении рейса.

## Архитектура

Решение состоит из статического веб-клиента, HTTP API и отдельного сервиса уведомлений. Nginx публикует клиент и проксирует `/api/` в API. API хранит основные данные в PostgreSQL, кэширует рейсы в Redis и записывает события в `outbox`. Фоновый издатель опрашивает outbox и передаёт события в Kafka. Notifier принимает события, сохраняет запланированные уведомления в PostgreSQL и отправляет их по SMTP.

### ADR-001: PostgreSQL как основное хранилище, Redis как кэш

**Решение.** Реляционные данные пользователей, аэропортов, воздушных судов, рейсов и подписок хранятся в PostgreSQL; Redis используется только для ускорения чтения и обновления данных о рейсах.

**Альтернативы.** Только PostgreSQL; документная БД; Redis как основное хранилище.

**Причины выбора.** Для предметной области важны внешние ключи, уникальность, ограничения значений и согласованное изменение связанных сущностей. PostgreSQL обеспечивает эти гарантии, а Redis снижает задержку часто выполняемого чтения, не становясь источником истины.

**Последствия.** Необходимо поддерживать согласованность кэша с PostgreSQL и предусматривать восстановление кэша после сбоя.

### ADR-002: асинхронные уведомления через outbox и Kafka

**Решение.** API сохраняет события подписки и изменения рейса в таблице `outbox`; фоновый издатель передаёт неотправленные записи в Kafka, а отдельный notifier планирует и отправляет письма.

**Альтернативы.** Синхронная SMTP-отправка внутри HTTP-запроса; непосредственная публикация в Kafka без промежуточного хранения; периодический поиск изменений в таблице рейсов.

**Причины выбора.** HTTP-запрос не зависит от скорости почтового сервера, компоненты API и отправки писем слабо связаны, а сохранённое событие можно повторно обработать после временной недоступности брокера.

**Последствия.** Доставка становится согласованной в конечном счёте; нужны идемпотентная обработка, мониторинг очереди и очистка обработанных записей. Текущая запись бизнес-данных и `outbox` ещё не объединена одной транзакцией, поэтому это ограничение следует устранить для полной гарантии доставки.

### ADR-003: веб-клиент без клиентского фреймворка

**Решение.** Интерфейс реализован на HTML, CSS и JavaScript-модулях и публикуется через Nginx.

**Альтернативы.** React, Vue или Angular; серверный рендеринг в Go.

**Причины выбора.** Интерфейс невелик, не требует сложного состояния и может поставляться как набор статических файлов без Node.js в runtime-образе.

**Последствия.** Сборка и доставка просты, но при росте интерфейса придётся вручную поддерживать маршрутизацию, компоненты и управление состоянием.

## Запуск

Необходимы GNU Make, Docker с плагином Docker Compose и заполненные файлы окружения:

- `backend/api/.env`, `backend/api/read.env` и `backend/api/migrate.env`;
- `backend/notifier/.env` и `backend/notifier/migrate.env`;
- `utils/.env` — только для генератора тестовых данных.

Запуск приложения:

```bash
make release
```

После запуска веб-интерфейс доступен на <http://localhost:8080>, API — на <http://localhost:8080/api/v1>, интерактивная документация API (Swagger UI) — на <http://localhost:8080/api/v1/docs/>, OpenAPI-спецификация в YAML — на <http://localhost:8080/api/v1/openapi.yml>. Единственное описание интерфейса API находится в [OpenAPI 3.0 спецификации](backend/api/cmd/docs/openapi.yml). Swagger UI читает её напрямую; аннотации в Go и генерация Swagger-файлов не используются.

Для отладки используйте `make debug`: дополнительно публикуются локальные порты PostgreSQL, Redis и Kafka, а фронтенд доступен напрямую на <http://localhost:3000> (порт можно изменить через `FRONTEND_PORT`). В режиме `make release` опубликован только порт общего Nginx — `127.0.0.1:8080`. API и notifier подключаются к инфраструктуре через Docker-сеть в обоих режимах.

### Балансировка API (пункт 1 задания)

Используются три экземпляра одного образа API и одна общая PostgreSQL:

| Экземпляр | Внутренний адрес | Прямой адрес в debug | Права БД | Вес чтения |
|---|---|---|---|---|
| Основной | `api:8080` | `127.0.0.1:8081` | Чтение и запись (`app_user`) | 2 |
| Только чтение | `api-read-1:8080` | `127.0.0.1:8082` | Чтение (`app_reader`) | 1 |
| Только чтение | `api-read-2:8080` | `127.0.0.1:8083` | Чтение (`app_reader`) | 1 |

Общий nginx направляет GET/HEAD к `/api/v1/` в группу с весами `2:1:1`, остальные методы — только в основной экземпляр. В штатном режиме основной обрабатывает примерно половину запросов чтения, каждый дополнительный — четверть. При отказах соотношение меняется; при недоступности основного запись не переносится на экземпляры чтения. API-запросы frontend на debug-порту 3000 также проходят через общий nginx.

Каждый API-ответ содержит `X-Backend-Instance`: `api`, `api-read-1` или `api-read-2`. Все экземпляры запускают одинаковый HTTP API без режима `READ_ONLY` и без проверок read/write в Go. Маршрутизацию методов выполняет nginx, а PostgreSQL ограничивает `app_reader` правами SELECT и включает `default_transaction_read_only` для этой роли. Redis остаётся общим кэшем; ограничения БД не запрещают заполнение кэша.

Outbox publisher запускается отдельно: сервис Compose `api-publisher` выполняет `/bin/publisher` из того же образа, что и API. Он использует подключение `app_user` из `backend/api/.env`, читает outbox, отправляет события в Kafka и отмечает их отправленными. HTTP API только сохраняет события в outbox и не запускает фоновый издатель; его запуск больше не зависит от доступности Kafka. Publisher не имеет HTTP-порта, ждёт PostgreSQL, Kafka и API-миграции и корректно завершает работу по SIGTERM. Должен работать один экземпляр publisher: текущий алгоритм не обеспечивает безопасное конкурентное извлечение событий несколькими workers.

Прямые debug-порты 8081–8083 обходят nginx. Попытку изменить бизнес-данные на экземпляре чтения отклонит PostgreSQL. Коды SQLSTATE `25006` и `42501` распознаются только в PostgreSQL-слое: он логирует техническую причину и возвращает ошибку репозитория. Usecase переводит её в собственную `ErrOperationNotPermitted`; HTTP-обработчик анализирует только эту ошибку usecase. Для рейсов между PostgreSQL и usecase дополнительно выполняется перевод в ошибку составного репозитория PostgreSQL/Redis. Ответ сохраняет HTTP 500 с нейтральным пояснением: `code: operation_not_permitted`, `msg: operation is not permitted`. Клиенту не сообщаются тип БД, режим подключения, SQL или имена таблиц. Другие внутренние ошибки возвращают `msg: internal error`. Ответа `403/read_only_instance` в API больше нет. Операции без записи в PostgreSQL, например генерация UUID, при прямом обращении разрешены. Для отдельного HTTP-отказа до API потребуется nginx-вход с фильтрацией методов перед экземплярами чтения.

Миграция `20260611191216_grant_privileges.sql` выдаёт `spectator` SELECT на существующие и будущие таблицы `api_schema`, а `admin` — полные права на таблицы этой схемы. `ALTER DEFAULT PRIVILEGES` действует на таблицы, создаваемые той же ролью, которая выполняет миграции (`postgres` в текущей конфигурации). Роли записи предметных областей получают права только на явно перечисленные таблицы; новые таблицы нужно добавлять в соответствующие GRANT. Миграция notifier аналогично настраивает текущие и будущие таблицы `notifier_schema` для `app_user`.

Миграция `20261014120000_create_api_reader.sql` создаёт пользователя чтения с фиксированным паролем и назначает ему `spectator`. Дополнительные экземпляры ждут успешного завершения мигратора. Все экземпляры наследуют один `JWT_KEY` из `backend/api/.env`.

Важно: исправления старых миграций применяются при развёртывании новой БД. Если эти миграции уже выполнены, Goose не запустит их повторно: для существующей БД нужна отдельная корректирующая миграция. Не удаляйте том с данными ради применения исправлений.

Фиксированный пароль `app_reader` — `reader_pswd`; он указан в SQL-миграции и строке подключения в `backend/api/read.env`. Оба read-only сервиса загружают этот файл после `backend/api/.env`, переопределяя только подключение к PostgreSQL. Файлы `*.env` исключены из Git. Эти учётные данные предназначены только для локальной разработки. Если миграция уже применена, изменение её файла не обновит пароль существующей роли: потребуется отдельная миграция с `ALTER ROLE`.

Проверки после запуска (приведены как инструкции, не выполняются автоматически):

```bash
# Смотреть X-Backend-Instance при последовательных GET через балансировщик.
curl -i http://localhost:8080/api/v1/status

# В debug прямое чтение должно вернуть 200.
curl -i http://localhost:8082/api/v1/status
curl -i http://localhost:8083/api/v1/status

# POST через балансировщик должен вернуть 200 и X-Backend-Instance: api.
curl -i -X POST http://localhost:8080/api/v1/uuids

# Проверить реальные права БД: can_read=true, can_insert=false, can_update=false,
# can_delete=false, can_truncate=false.
docker compose -f backend/docker-compose.yml exec postgres psql -U postgres -d airline_tracker -c "SELECT has_table_privilege('app_reader', 'api_schema.flights', 'SELECT') AS can_read, has_table_privilege('app_reader', 'api_schema.flights', 'INSERT') AS can_insert, has_table_privilege('app_reader', 'api_schema.flights', 'UPDATE') AS can_update, has_table_privilege('app_reader', 'api_schema.flights', 'DELETE') AS can_delete, has_table_privilege('app_reader', 'api_schema.flights', 'TRUNCATE') AS can_truncate;"
```

Репликация БД и `/mirror` в этом пункте не реализуются.

```bash

Эти каталоги и локальная установка CLI игнорируются Git. Из каталога `backend` используется та же команда `make test`.

Для измерения покрытия условий установите `gobco` в каталог из `PATH`:

```bash
go install github.com/rillig/gobco@v1.3.4
```

Из каталога `backend`:

```bash
make gobco
make gobco PACKAGE=./internal/flight/infra/redis
```

По умолчанию проверяется `flight/usecase`. `gobco` обрабатывает один пакет за запуск; `PACKAGE` задаётся относительно `backend/api`. Скрипт использует временный `go.mod` с подключением локального модуля `shared` и удаляет временные файлы после запуска. Из корня проекта используйте `make backend-gobco`.

Для запуска одного теста по названию из каталога `backend`:

```bash
make test-name TEST=TestFlightUsecase_UpdateFlight
make test-name PACKAGE=./internal/flight/infra/redis TEST=TestRedisDB_SaveFlight
```

По умолчанию используется пакет `flight/usecase`. Запускаются выбранный тест и его подтесты с подробным выводом и без кеширования результата. Из корня проекта используйте `make backend-test-name TEST=TestFlightUsecase_UpdateFlight`.

Пример Chicago-теста репозитория:

```bash
make test-name TEST=TestRedisDB_UpdateFlight_Chicago
```

Он проверяет сохранённое состояние через настоящий `RedisDB` и клиент Redis. Тестовый сервер `miniredis` работает в памяти внутри процесса теста на временном локальном порту. Mock-ожидания не используются; внешние сервисы и интернет для выполнения теста не нужны.
